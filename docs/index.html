Finding Content Pages Worth Refreshing

A practical machine learning approach to identifying content pages that may need attention, using search and engagement signals.

Abstract

Content teams can have a large number of pages to look after, but limited time to review all of them. This project asks whether existing search and engagement data can be used to find pages that show signs of decline and help decide which ones are worth looking at first. I built a classification model using signals such as impressions, clicks, search position, engagement and content age, while keeping information from the future out of the features. On the honest validation split, the model reached a Precision@50 of 0.680 compared with 0.380 for the baseline. The result suggests that the model can make the review process more focused, but it should be treated as a prioritisation tool for human review rather than a system that automatically decides which content should be changed.

1. The Question

The practical problem behind this project is simple: when there are many content pages to review, it is difficult to know where to start. A page can lose search visibility or engagement for several different reasons, and not every change means that the page needs to be rewritten. I wanted to see whether the data already available about these pages could help narrow the list down and give a content team a sensible place to start.

Research question: Can search performance, engagement and content-age signals be used to rank pages that are more likely to show signs of decline?

This is a ranking problem rather than an attempt to completely automate content decisions. A useful model should help a person decide where to spend their time first.

2. Data

I used the anonymized content-refresh dataset provided for the FlyRank ML Internship. The working dataset contains 30,000 content pages and 45 columns, with one row representing one content page.

The dataset includes search-performance information such as impressions, clicks, CTR and average position, along with content and engagement information such as content age, word count, engagement rate and days since the last update.

Release and tables

For the earlier experiments, I worked with the small starter dataset included with the internship repository. For the later feature- engineering work, I also worked with the internship warehouse release through DuckDB, which allowed the data to be queried without loading the entire release into memory.

The warehouse work used the client, content, daily performance and 90-day content-query tables. This was useful for building page-level features from larger amounts of historical performance data.

Date windows

The page-level dataset contains 90-day performance fields, including impressions, clicks, sessions and engagement measures. I also used 30-day and previous-30-day values when comparing recent performance with the preceding period.

In the warehouse experiment, I also created a 90-day feature window and compared the recent 45 days with the preceding 45 days. I added position volatility as an extra feature to capture how much a page's average search position changed over that period.

What I excluded

I excluded fields that directly contained or revealed the outcome from the model features. In particular, trend direction, trend percentage and the decline label were not used as predictors.

I also avoided using information from future performance windows when building the features. The goal was to make sure the model only used information that could reasonably have been available when making the ranking.

Finally, the paper only presents anonymized and public-safe information. Client names, private URLs and private search queries are not included.

3. Methodology

Features

I wanted the model to use signals that would actually be available when deciding which pages deserve attention. The features included search performance, engagement and content characteristics such as impressions, clicks, CTR, average position, engagement rate and content age.

In the warehouse experiment, I also tested position volatility as an additional feature. This was calculated from the variation in average search position over the 90-day window.

Label

I treated the task as a binary classification problem. A page was labelled as declining when its trend direction was "down". The model then learned to distinguish declining pages from the other pages using the available features.

Baseline

Before using machine learning, I created a simple rule-based baseline. This gave me something straightforward to compare the model against. The baseline used signals such as CTR, search position and recent impression changes to prioritise pages.

I used Precision@50 as the main metric because the practical goal is to create a short list of pages for review. If a team only has time to investigate 50 pages, the useful question is how many of those first 50 pages are actually relevant.

Model

I used a Random Forest classifier for the machine learning model. It can combine several signals and capture relationships that a single hand-written rule might miss. I used 200 trees with a fixed random seed so that the experiment could be reproduced.

Validation

I initially experimented with a normal train/test split, but for the more realistic evaluation I used a client-grouped split. Grouping by client means that pages from the same client cannot appear in both the training and test sets.

The final split contained 24 clients in training and 8 clients in testing, with no clients shared between the two groups. This gives a better indication of how the approach might perform on a client that was not seen during training.

Leakage checks

I checked the feature list for variables that could reveal the target directly. Fields such as trend direction, trend percentage and the decline label were excluded from the model inputs.

I also checked the time windows used to create features so that future outcome information was not accidentally fed into the model. These checks are important because a model can appear much better than it really is if information about the answer leaks into the inputs.

4. Results

The final model was evaluated on an honest validation split using Precision@50. The idea here is pretty simple: if the team only has time to look at a small number of pages, are the pages at the top of the model's list actually more likely to be declining?

The model reached a Precision@50 of 0.680 on the honest split, compared with 0.380 for the baseline. That is a 0.300 improvement in Precision@50. What I take from the results: The model looks useful as a prioritisation tool. It improves on the baseline on the same metric and gives the content team a smaller group of pages to investigate first. It does not tell us that a particular page definitely needs a refresh, or that a refresh will cause better performance.

5. Limitations

There are several reasons not to overstate these results. First, this is observational data, so the model can identify patterns and associations but cannot prove that one factor caused a page to decline.

Second, Precision@50 only tells us about the quality of the highest ranked pages. It does not mean that every page outside the top 50 is unimportant.

Finally, a page being identified as declining does not automatically mean that refreshing it is the correct solution. Search demand, competition, seasonality, content quality and other factors can all affect performance.

Honest interpretation: The model should be used to prioritise human review, not to automatically decide which content should be changed.

6. Ranked Recommendations

Based on the analysis, I would use the model as a first-pass queue for a content team.

1. Start with the highest-ranked pages Review the top of the model's queue first because these pages have the strongest combination of signals associated with decline.
2. Check the reason before changing anything A ranking is a starting point, not a diagnosis. The reviewer should look at the page, its search position, traffic trend and intent before deciding what action makes sense.
3. Prioritise pages where the decline is meaningful A small movement in traffic does not necessarily justify a content refresh. Larger or more consistent changes deserve more attention.
4. Keep a human in the loop The model should recommend what to inspect first. The final decision about rewriting, updating, merging or leaving a page alone should remain with a person.
5. Recheck the model over time Search behaviour changes, so a ranking system should not be assumed to stay accurate forever. Its performance should be monitored and the model reconsidered when the underlying data changes.
